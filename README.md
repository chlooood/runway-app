# Runway

[![CI](https://github.com/chlooood/runway-app/actions/workflows/ci.yml/badge.svg)](https://github.com/chlooood/runway-app/actions/workflows/ci.yml)

A savings and cash-flow forecaster for students with irregular income: co-op terms that pay, school terms that don't, and a move between cities along the way. It answers one question: **will I have enough saved by the time I leave for exchange, and will it last?**

**Stack:** FastAPI · SQLAlchemy 2 · Alembic · PostgreSQL · React · TypeScript · Recharts · GitHub Actions

## The demo scenario

A student works a summer co-op in Toronto (May–Aug), goes back to Vancouver for a school term with no income (Sept–Dec), then leaves for an exchange term in Lyon (Jan–Apr). All data is synthetic, generated by a deterministic seed script; none of it is real financial data.

With the seeded data, Runway shows:

- **$13,576** projected by departure on Jan 4, against a **$7,764** goal. The goal is calculated from the Lyon budget: flights, deposit, and living costs for Jan 5–Apr 30.
- About **$5,942** left at the end of the exchange, never dipping below $0.
- Switching the home baseline from Vancouver to Toronto (higher cost of living) lowers the end balance to **$5,368**.

## What it does

- **Goal progress:** the projected balance on the goal date compared with the target, with an on-track / short badge.
- **Cash flow chart:** actual balance history, a dashed projection, the goal line, and the exchange term shaded, including the flights-and-deposit drop on departure day.
- **City toggle (Toronto / Vancouver):** switches the cost-of-living baseline used for the projection.
- **Spending breakdown:** average monthly spend per category for the selected city.
- **Suggested cuts:** if the goal is short, the monthly shortfall is split across flexible categories (dining, entertainment, …), never fixed ones like transit.
- **Runs-out warning:** if the balance would drop below $0 during the exchange, the app says roughly when.

## Engineering highlights

- **Layered backend.** SQLAlchemy models (database shape) are kept separate from Pydantic schemas (API shape), and ORM objects are never returned directly. Routes, business logic and database setup each have their own folder, and `main.py` only wires them together.
- **Testable, explainable forecast.** The projection is a pure function in [`services/forecast.py`](backend/app/services/forecast.py), with no database or HTTP code. Its docstrings state its assumptions and what it doesn't handle. It has [15 pytest cases](backend/tests/test_forecast.py) with hand-checkable numbers. No ML: every number can be traced back to a rule.
- **Real migrations.** Alembic manages every schema change. Migration [`0003`](backend/alembic/versions/0003_add_users_and_user_id_ownership.py) adds a required `user_id` to four tables that already contain data. Autogenerate's version would fail on a populated database, so it was rewritten to follow expand, backfill, contract. It's tested on populated data, including a downgrade/upgrade round trip.
- **Validation in depth.** A rule like "a stay can't end before it starts" is enforced in three places: the Pydantic schema, the PATCH handler (which checks the merged dates), and a database `CHECK` constraint. Bad input returns a 422 rather than a 500.
- **Ownership checks.** Every route is scoped to the current user through a FastAPI dependency. Another user's rows return the same 404 as missing ones, so ids can't be probed. With no login yet, there's a single demo user, and the dependency is where real authentication would plug in.
- **Typed frontend.** TypeScript runs in `strict` mode with no `any`. The backend sends money as decimal strings so it never loses precision, and one adapter layer converts them to numbers before any component sees them. Fetching lives in a hook that ignores stale responses, so quickly switching cities can't show the wrong city's data.
- **Measured before optimizing.** The page loaded slowly, and timing the requests traced it to Windows resolving `localhost` to IPv6 first. That added about 2 s per request against an API answering in under 50 ms. The fix was a config change, not caching.
- **CI.** [GitHub Actions](.github/workflows/ci.yml) applies every migration to a fresh Postgres, runs `alembic check` to confirm the models and migrations agree, runs the tests, and lints, type-checks and builds the frontend on every push.

The reasoning behind each step is logged in [`BUILD_LOG.md`](BUILD_LOG.md).

## How the forecast works

For each future day:

```
balance += known income that day
         − daily spend: a planned stay's monthly budget (e.g. Lyon), otherwise the
           historical average monthly spend for the selected home city
         − a stay's upfront cost (flights, deposit) on its first day
```

The goal is judged on the balance at its target date. The projection keeps going to the end of the last planned stay, so it can report the end-of-exchange balance and whether the money runs out. Exchange costs are modelled as *planned stays* with a budget, kept separate from *expenses*, which are actuals only. That way planned costs never skew the historical averages.

## Running it locally

Prerequisites: Docker, Python 3.11+, Node 20.19+ (or 22.12+).

**1. Start Postgres**

```bash
docker compose up -d --wait
```

The credentials are dev-only defaults (`runway` / `runway`, database `runway`, port 5432). You can override them with `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` or `POSTGRES_PORT`.

**2. Backend** (from `backend/`)

```bash
python -m venv venv
venv\Scripts\activate          # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env           # Windows: copy .env.example .env
alembic upgrade head
python -m scripts.seed
uvicorn app.main:app --port 8000
```

The API docs are at http://127.0.0.1:8000/docs.

**3. Frontend** (from `frontend/`)

```bash
npm install
cp .env.example .env           # Windows: copy .env.example .env
npm run dev
```

Then open http://localhost:5173.

### Useful commands

| Command (from `backend/`) | What it does |
|---|---|
| `python -m pytest` | Runs the forecast unit tests |
| `python -m scripts.seed --reset` | Wipes all rows and re-seeds; without `--reset` it refuses to overwrite existing data |
| `python -m scripts.seed --as-of 2026-09-29 --seed 7` | Seeds as of a fixed date with a different random seed (the same inputs always give the same data) |
| `alembic check` | Confirms the models and migrations agree |

## Project structure

```
backend/
  app/
    models/         SQLAlchemy models (database shape)
    schemas/        Pydantic schemas (API request/response shape)
    routers/        FastAPI routes, one file per resource
    services/       Business logic (the forecast), no DB or HTTP code
    config.py       All environment config
    database.py     Engine, session, get_db dependency
    dependencies.py get_current_user (single demo user; the hook for real auth)
    main.py         App setup and router registration only
  alembic/          Migrations (0001 core tables, 0002 planned stays, 0003 users)
  scripts/seed.py   Deterministic synthetic data (Faker, seeded)
  tests/            Unit tests for the forecast service
frontend/
  src/
    api/            Typed API client; converts wire format (money as strings) to app types
    components/     CityToggle, GoalProgressCard, CashFlowChart, CategoryBreakdown
    hooks/          useRunwayData (fetching, loading/error state)
.github/workflows/  CI
docker-compose.yml  Local Postgres
BUILD_LOG.md        Step-by-step engineering log
```

## API

| Method | Path | Notes |
|---|---|---|
| `GET` `POST` | `/income-events`, `/expenses`, `/goals`, `/planned-stays` | `GET /expenses?city=&category=` filters |
| `GET` `PATCH` `DELETE` | `/{resource}/{id}` | 404 if missing or owned by another user |
| `GET` | `/goals/{id}/forecast?city=&as_of=` | `city` = home baseline; `as_of` defaults to today |

## Limitations and what I'd build next

These limits are deliberate, and documented in the forecast service:

- **Authentication.** There's a single demo user with no login. Next step: real auth behind `get_current_user`.
- **Currency.** Stay budgets are assumed to be in CAD; the Lyon budget is a synthetic EUR estimate converted at 1.5 CAD/EUR. Next step: per-stay currency with exchange rates.
- **Known future bills.** Future-dated expenses, such as a tuition bill, are ignored rather than subtracted. Next step: scheduled expenses, mirroring scheduled income.
- **Simple averages.** Spending rates are plain averages, and a partly elapsed month counts as a whole month. There's no inflation, interest, or income tax modelling.
